# Results: direct tool calls vs code execution (ticketdesk)

First live run, 2026-11-25. Raw data: `docs/results/ticketdesk-medium-2026-11-25.jsonl` (24 runs, one JSON line each). Reproduce with:

```
uv run mcpx run --target ticketdesk --arm both --task all --runs 3 \
  --out runs/ticketdesk.jsonl --reasoning-effort medium
uv run mcpx report runs/ticketdesk.jsonl
```

## What the numbers say

- **Tokens and cost: the code arm wins on every task.** The biggest gap is task B, where the direct arm pushed hundreds of full ticket bodies through the model: about 292k prompt tokens against 18k. Cost followed, 12x cheaper on B.
- **Task A shows the schema overhead in isolation.** One lookup, yet the direct arm carried all 30 tool schemas on each of its 2 calls (about 6.5k tokens per call). The code arm read one wrapper file instead.
- **Latency: the code arm did not win.** It took more model turns (A 4 vs 2, B 9 vs 3, D 5 vs 3) and was slower on A, B and D. Only C was marginally faster. Saving tokens cost round trips here.
- **Correctness was not traded away.** 24/24 correct, including the code arm on every task.

## Where this is weaker than it looks

- **Tasks C and D do not test what they were designed to test.** C was meant to force about 30 chained calls, but `list_tickets` already returns each ticket's `reviewers`, so the direct arm solved it in 1 tool call. D was meant to force paging through the activity log, but the server has a `list_deploys` shortcut tool, so the direct arm used it. The 41% and 26% figures mostly measure schema overhead, not the join or the loop. Only A (overhead) and B (large intermediate results) test the intended mechanism. Fixing C and D means removing those shortcuts from the server or redesigning the tasks.
- **One model, one dataset, 3 runs per cell.** Run-to-run spread is visible (B direct prompt tokens 150k to 292k; one C direct run produced 7,037 output tokens against about 1,250 for the others). Ratios are indicative, not precise.
- **Cached-token counts vary a lot between runs** (0 to 14k on the same task), so the "cost with cache reads" column is noisy; the list cost is the stable figure.
- **Prices are peak prices** and the provider is not pinned, so absolute dollar figures are upper bounds and could shift between providers.
- **The reasoning effort `medium` is requested, not verified.** LiteLLM sends it to OpenRouter as `reasoning_effort`; whether the provider honours it has not been checked against reasoning-token counts.
- **Not the article's 98.7%.** That figure is for a workload with thousands of tool schemas. This server has 30, so the schema overhead here is modest; task B is the closest analogue and shows 94% fewer prompt tokens.
